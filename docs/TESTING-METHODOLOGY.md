# 软件项目测试指导方法论

这是一套可复用到不同项目的测试决策方法。它的目标不是让每次改动都运行最多的测试，而是用与风险相称的最小成本，证明本次改动没有破坏目标行为。

## 1. 核心原则

### 1.1 测试服务于风险，而不是服务于数量

测试范围由改动影响的范围决定。没有影响到的模块，不应因为“顺便”而加入验证；能够由更快、更直接的检查证明的问题，不必升级为完整测试。

### 1.2 默认最小验证

日常开发默认只执行与当前改动直接相关的最小验证：

- 细小的视觉、间距、颜色、文案调整：通常不运行测试，必要时确认页面能渲染、显示无明显错误；
- 前端行为、状态或交互调整：验证受影响的组件或流程，并确认页面正常渲染；
- 后端模块或 API 调整：只验证受影响模块的最小单元或接口行为；
- 跨模块、持久化、并发或发布链路调整：补充能够覆盖该边界的最小集成或冒烟检查；
- 全量测试：只有项目负责人或用户明确要求时才执行，除非项目已有不可绕过的强制质量门禁。

“没有运行测试”不是遗漏。只要说明原因、替代检查和剩余风险，就是可审计的工程决策。

### 1.3 测试必须回答具体问题

每项验证都应对应一个问题，例如：

- 这个组件还能否渲染？
- 这次修改的状态转换是否正确？
- 这个 API 是否仍返回约定结果？
- 旧数据、错误输入或失败依赖是否仍能恢复？
- 这个构建是否真的包含可运行的产物？

无法说明要证明什么的测试，通常不应加入本次任务。

## 2. 先判断改动类型

在选择命令前，先给改动归类。一个改动可以同时属于多个类别，此时取覆盖风险的最小组合。

| 改动类型 | 默认验证 | 通常不需要 |
|---|---|---|
| 纯视觉细节：颜色、间距、圆角、阴影、图标尺寸 | 页面渲染或人工显示确认 | 全量单测、后端测试、完整构建 |
| 文案、翻译、静态布局 | 受影响页面显示确认，检查关键语言是否溢出 | 与业务逻辑无关的测试套件 |
| 前端组件行为或交互 | 受影响组件/流程的最小测试，必要时做一次页面渲染确认 | 不相关页面、全量 E2E |
| 前端状态管理、数据转换 | 对应 store、composable 或转换函数的单测 | 无关组件和后端模块 |
| 后端业务模块 | 受影响模块的最小单测 | 全量服务链路 |
| API 请求/响应或权限边界 | 受影响接口的 API 测试，必要时覆盖一个错误路径 | 无关端点和完整系统测试 |
| 数据库、迁移、索引或持久化 | 对应数据库行为和一次直接边界检查 | 不相关业务流程 |
| 跨层流程、异步、并发或缓存 | 覆盖真实边界的最小集成测试 | 与问题无关的全量回归 |
| 构建、打包、启动或发布配置 | 受影响链路的最小构建/冒烟检查 | 仅因改配置就运行全部业务测试 |

## 3. 测试分层

测试层级越高，成本通常越高、定位越慢。因此优先选择能够直接证明问题的低层级测试。

### 3.1 单元测试

验证一个函数、类或纯业务规则。适合数据转换、边界判断、版本解析、过滤条件、错误映射等逻辑。

特点：快、稳定、定位清晰。应隔离网络、真实文件、屏幕、时间和生产数据库。

### 3.2 组件测试

验证一个 UI 组件的渲染、状态变化、交互和可访问性契约。适合按钮、表单、筛选器、弹窗、列表状态等局部行为。

前端改动至少应确认受影响组件可以渲染；只有行为或状态改变时，才需要补充交互断言。

### 3.3 集成测试

验证两个或多个真实模块之间的边界。适合 API 到服务、服务到数据库、搜索到索引、前端到后端等流程。

集成测试只应在改动触及边界、单元测试无法证明链路，或历史问题明确发生在边界时加入。

### 3.4 端到端测试

从用户入口验证完整流程。适合登录、支付、创建/编辑/删除、关键发布流程等高风险路径。

不要为了一个局部样式或函数改动运行整套端到端测试；除非改动改变了完整流程的入口、导航或关键状态。

### 3.5 构建与冒烟检查

构建成功不等于程序可用。发布或打包改动至少要确认：产物存在、能启动、关键健康检查通过，或能够完成项目约定的最小冒烟流程。

## 4. 最小验证决策流程

可以按以下顺序选择验证：

1. **列出直接影响的文件和行为。** 不要从“整个项目”开始估计范围。
2. **判断是否只是视觉或文案。** 如果是，通常只做渲染/显示确认。
3. **寻找离问题最近的测试缝隙。** 优先函数单测，其次组件测试，再其次集成或端到端。
4. **只覆盖本次改变的状态。** 同时考虑一个最重要的失败或边界情况。
5. **检查是否存在直接副作用。** 例如数据库写入、网络请求、异步竞态、文件生成或发布产物。
6. **执行最小命令并记录结果。** 不因测试“顺手”而扩大范围。
7. **若最小验证失败，先修复；若成功，再决定是否需要扩大范围。** 默认不自动升级到全量测试。

### 4.1 一个简单的风险矩阵

| 影响范围 | 风险较低 | 风险较高 |
|---|---|---|
| 局部组件/函数 | 静态检查、单元或组件测试 | 增加边界和失败路径 |
| 跨模块链路 | 直接集成检查 | 集成检查 + 关键端到端路径 |
| 数据、权限、支付、删除等高后果操作 | 不可仅靠视觉确认 | 必须覆盖成功、失败和恢复 |
| 构建/发布产物 | 构建成功检查 | 构建 + 启动/健康检查 + 产物核对 |

风险矩阵用于避免两个极端：小改动被过度测试，或高后果改动只做表面确认。

## 5. 前端改动的指导

### 5.1 视觉细节

颜色、间距、阴影、模糊、图标尺寸、圆角和文字微调，默认不运行测试。必要时只确认：

- 页面能正常渲染；
- 目标元素显示，没有明显遮挡、溢出或布局跳动；
- 窄屏或深色主题没有明显破坏（若项目支持）。

### 5.2 组件行为

当改动涉及点击、选择、输入、加载、错误、关闭、提交或状态切换时，至少验证受影响行为。例如：

- 点击筛选条件是否产生预期结果；
- “应用”按钮是否仍能提交并关闭；
- 错误输入是否保留在正确状态；
- 加载期间按钮是否避免重复提交；
- 键盘和可访问名称是否仍然可用。

不需要因为一个组件行为变化就运行所有页面的测试；只覆盖直接相关的组件和流程。

### 5.3 页面渲染确认

组件测试通过后，仍应在页面入口确认一次真实组合，尤其是涉及布局、浮层、滚动、响应式或层级关系的改动。渲染确认可以是开发页面、截图、浏览器检查或项目已有的轻量冒烟流程。

## 6. 后端改动的指导

- 业务规则变化：运行对应服务的单元测试；
- API 契约变化：运行受影响接口的成功和关键失败用例；
- 数据库或索引变化：验证读写、迁移和直接同步边界；
- 异步、重试或并发变化：覆盖成功、失败、超时或旧请求不覆盖新请求的路径；
- 外部服务调用：默认使用 fixture、mock 或替身，不要求真实密钥；
- 只有跨层影响明确时，才从单测扩展到集成测试。

测试应使用临时目录、隔离数据和可控依赖，不写入真实用户数据或开发者本机数据目录。

## 7. 回归测试与缺陷修复

修复一个可稳定复现的缺陷时，优先在最接近实际调用位置的测试缝隙中加入回归断言：

1. 先记录原始失败现象；
2. 把现象缩小为一个稳定的输入和预期；
3. 先确认回归测试确实能失败；
4. 修改代码使其通过；
5. 再运行原始最小验证，确认不是只修好了测试样例。

如果当前架构没有足够真实的测试缝隙，应在交付说明中指出，而不是用过于浅层的测试制造虚假安全感。

## 8. 什么时候不运行测试

以下情况通常可以不运行测试：

- 只改了静态样式、间距、颜色、阴影或图标大小；
- 只改了不影响逻辑的文案或排版；
- 只更新了设计说明、测试说明或发布说明；
- 改动没有触及任何可执行代码，且没有项目强制检查要求。

不运行测试时仍应进行必要的静态检查或人工确认，并在总结中明确写出：

```text
验证：未运行测试；本次为视觉/文档细节调整，已完成静态检查或页面显示确认。
```

## 9. 全量测试的使用边界

全量测试适合解决“项目整体是否仍可发布”这一问题，不适合成为每次小改动的默认动作。建议只在以下场景执行：

- 项目负责人或用户明确要求；
- 即将进行正式发布，且项目流程明确把全量测试作为门禁；
- 改动跨越多个核心层，无法通过局部验证覆盖；
- 大规模重构、依赖升级或基础设施变化；
- 安全、数据完整性或高后果业务变更。

全量测试仍应记录实际命令、通过数、失败数和失败原因；不能只写“已测试”或“环境问题”。

## 10. 测试质量底线

- 测试结果可重复，不依赖执行顺序；
- 测试数据与真实用户数据隔离；
- 网络、时间、随机数和外部服务在需要时可控；
- 测试名称说明行为和预期，而不是说明实现细节；
- 失败信息足以定位问题；
- 不为了通过测试而削弱产品行为；
- 新增测试覆盖真实风险，而不是单纯增加数量；
- 测试失败时保留失败现场，并报告下一步需要什么信息。

## 11. 交付时的验证报告模板

每次交付只需简要说明以下内容：

```text
改动范围：<文件、模块或用户行为>

验证：
- <实际运行的最小命令>：<通过数量/结果>
- <页面渲染或冒烟确认>：<结果>

未运行：
- <未运行的更大范围测试>：<因为与本次改动无关/用户未要求/不适用>

剩余风险：<无，或说明尚未覆盖的边界>
```

合格的测试报告不是命令清单，而是让读者知道：改了什么、验证了什么、没有验证什么，以及为什么这样安排。

## 12. 可复制到新项目的测试政策模板

```text
默认原则：只运行与当前改动直接相关的最小验证。

视觉/文案细节：不运行测试；做页面渲染或显示确认。
前端行为变化：运行受影响组件/流程的最小测试，并确认真实页面渲染。
后端模块变化：运行受影响模块的最小单元或 API 测试。
跨层/数据/异步变化：补充直接相关的集成或失败路径检查。
构建/发布变化：执行受影响链路的最小构建和冒烟检查。
全量测试：仅在负责人明确要求或项目既定门禁要求时运行。

测试隔离：不使用真实密钥、真实用户数据或生产数据目录。
交付报告：记录实际运行、跳过的验证、结果和剩余风险。
```

这套方法的最终标准很简单：小改动快速、明确地验证；高风险改动覆盖关键边界；任何未验证的部分都诚实可见。
