# 软件版本号统一控制方法论

本文提供一套可迁移到桌面软件、Web 服务、移动应用、命令行工具和多模块项目的版本管理方法。重点不是某一种构建工具，而是让软件的所有组成部分对“当前版本是什么”得到同一个答案。

## 1. 版本管理的目标

良好的版本控制需要同时做到四件事：

1. **唯一**：一个版本只有一个权威来源。
2. **一致**：界面、安装包、程序文件、服务端和发布页面显示同一版本。
3. **可解释**：仅看版本号就能判断兼容性级别和发布通道。
4. **可追溯**：版本号、源代码标签和发布产物能够一一对应。

核心原则可以概括为：

> 版本号只决定一次，其余位置只同步、派生或展示，不再各自决定。

## 2. 建立唯一版本事实源

项目必须指定一个“版本事实源”。它是唯一允许人工决定版本号的位置，其他文件中的版本字段都属于镜像或派生值。

版本信息按职责分为三类：

| 类型 | 含义 | 管理规则 |
|---|---|---|
| 权威版本 | 项目正式认可的完整版本号 | 只能在一个位置维护 |
| 镜像版本 | 因不同语言、框架或打包系统而必须存在的副本 | 由统一工具同步，不单独手改 |
| 派生版本 | 从权威版本计算出的文件名、数字版本、显示文本等 | 构建或运行时生成 |

事实源放在哪里并不重要，可以是清单文件、专用版本文件或发布配置。重要的是项目必须明确写下：

- 哪个位置拥有版本决定权；
- 哪些位置只是镜像；
- 哪些值由版本号派生；
- 使用什么方式检查它们是否一致。

### 2.1 常见版本消费者

一个软件项目通常不止一个地方需要识别版本：

| 消费位置 | 应使用的版本 |
|---|---|
| 应用“关于”页面、设置页、命令行输出 | 完整版本号 |
| 前端与后端的运行状态接口 | 同一完整版本号 |
| 安装包名称和下载页面 | 完整版本号 |
| 操作系统文件属性 | 平台允许时使用完整版本；受限时使用派生数字版本 |
| 日志、崩溃报告和诊断信息 | 完整版本号，必要时附构建标识 |
| 源代码标签 | 完整版本号加统一前缀，例如 `v` |
| 发布页面和更新源 | 与标签完全一致的版本号 |

任何组件都不应通过“自己写一个默认值”解决版本缺失。确实需要开发环境回退值时，应明确显示为 `development`、`unknown` 等非发布版本，避免把无法识别的构建伪装成正式版本。

## 3. 统一版本传播方式

推荐采用以下传播关系：

```text
版本决策
  → 权威版本源
  → 同步所有必要镜像
  → 校验镜像一致性
  → 构建时派生平台版本和产物名称
  → 运行时展示同一完整版本
  → 创建对应源代码标签和发布记录
```

控制重点不是增加更多版本文件，而是减少独立编辑点。每增加一个必须手工修改的位置，漏改概率都会上升。

### 3.1 同步规则

- 统一版本工具负责更新全部镜像。
- 同步后立即执行一致性校验。
- 构建流程只读取已同步的版本，不临时猜测或改写它。
- 发布构建发现不一致时应停止，而不是选择其中一个继续。
- 版本镜像应随源码提交，使任意提交都能说明自己将构建成什么版本。

### 3.2 平台限制的处理

有些平台只接受纯数字版本，例如四段数字；项目对外版本却可能包含 `preview`、`rc` 等文字。这时不应放弃统一版本规范，而应建立明确映射：

```text
公开版本：2.4.0-preview.20260825
平台数字版本：2.4.0.0
```

完整版本仍用于界面、安装包名称、日志、标签和发布页面；数字版本只服务于受限的平台字段。两者是“完整身份”和“平台表示”的关系，不是两个独立版本。

## 4. 版本号命名规范

推荐使用语义化版本：

```text
主版本.次版本.修订版本
MAJOR.MINOR.PATCH
```

例如：`3.2.5`。

### 4.1 三段数字的含义

| 变化 | 何时增加 | 示例 |
|---|---|---|
| 主版本 MAJOR | 出现明确的不兼容变化，用户或集成方需要迁移 | `2.6.4 → 3.0.0` |
| 次版本 MINOR | 增加向后兼容的新能力或显著扩展 | `2.6.4 → 2.7.0` |
| 修订版本 PATCH | 修复问题、小幅优化，且不改变既有兼容关系 | `2.6.4 → 2.6.5` |

版本升级应反映用户和集成方需要承担的变化，而不是代码行数、开发时长或团队主观上的“改动很大”。

### 4.2 预发布版本

尚未达到正式稳定状态的版本，在三段数字后增加预发布标识：

```text
2.7.0-dev.20260825
2.7.0-preview.20260825
2.7.0-rc.1
```

推荐约定：

- `dev`：团队内部开发构建，稳定性不承诺；
- `preview`：可交付给外部体验者的功能预览；
- `rc`：正式版候选，只接受阻断发布的问题修复；
- 无后缀：正式稳定版本。

预发布版本的基础数字应指向它准备成为的正式版本。例如，新功能计划进入 `2.7.0`，预览版应命名为 `2.7.0-preview...`，而不是继续挂在已经发布的 `2.6.x` 下。

日期适合表达构建批次，序号适合表达同一阶段的先后。项目可以选择日期、序号或二者组合，但选定后应保持一致，不要在同一通道混用多种规则。

### 4.3 构建标识

构建标识用于区分“功能版本相同、构建批次不同”的产物，例如：

```text
2.7.0-preview.20260825+build.184
```

它适合内部追踪，不应承担兼容性含义。若下载、更新或平台商店会忽略构建标识，就应使用能被这些系统可靠识别的预发布序号。

## 5. 如何决定下一个版本号

版本决策可以按以下顺序进行：

1. 是否产生不兼容变化？如果是，增加主版本。
2. 是否增加向后兼容的新能力？如果是，增加次版本。
3. 是否只是修复或兼容范围内的优化？如果是，增加修订版本。
4. 当前是否达到正式稳定标准？如果没有，增加对应发布通道后缀。

决策示例：

| 当前版本 | 变化 | 下一个版本 |
|---|---|---|
| `1.8.2` | 修复崩溃 | `1.8.3` |
| `1.8.2` | 增加兼容的新功能 | `1.9.0` |
| `1.8.2` | 删除旧接口或改变数据格式 | `2.0.0` |
| `1.8.2` | 新功能尚在公开试用 | `1.9.0-preview...` |
| `1.9.0-preview...` | 准备正式发布 | `1.9.0` |

纯文档、构建脚本或内部重构通常不改变面向用户的版本规划；但只要重新发布了可下载产物，该产物仍应具有可区分、可追溯的版本身份。

## 6. 发布通道设计

通道代表稳定性和受众，不应与版本大小混为一谈。

| 通道 | 主要受众 | 允许的变化 | 典型命名 |
|---|---|---|---|
| 开发版 | 开发者和内部测试 | 快速变化，可不稳定 | `X.Y.Z-dev...` |
| 预览版 | 体验用户、早期采用者 | 功能基本完整，允许继续调整 | `X.Y.Z-preview...` |
| 候选版 | 发布验收人员 | 原则上只修复阻断问题 | `X.Y.Z-rc.N` |
| 正式版 | 全体用户 | 满足稳定和兼容承诺 | `X.Y.Z` |

每个通道应明确：

- 谁可以获得；
- 稳定性承诺是什么；
- 哪类改动可以进入；
- 如何升级到下一个通道；
- 是否允许自动更新到其他通道。

同一份源代码可以面向不同通道构建，但每个发布产物必须拥有明确且唯一的版本身份。

## 7. 标签不变性

源代码标签表示“这个版本对应的精确源码”。因此：

> 一个已经推送或发布的版本标签，应被视为不可变。

标签一旦被外部系统、构建流程或用户看到，就不应再移动到另一个提交。否则，同名版本可能对应不同源码和不同二进制文件，校验值、问题报告和审计记录都会失去可信度。

推荐规则：

- 标签名称必须与权威版本一致，例如版本 `2.7.0` 对应标签 `v2.7.0`。
- 标签只在版本同步和一致性校验完成后创建。
- 构建系统从标签指向的源码构建，而不是从不断变化的主分支构建。
- 已发布标签发现问题时，创建新的版本标识，不覆盖旧标签。
- 只有在标签从未对外发布、从未生成产物，并且团队有明确许可时，才考虑删除后重建；此类例外必须留下记录。

标签不变性并不是形式主义，而是让“版本号 = 源码 = 构建产物”长期成立的基础。

## 8. 不要混淆不同类型的版本

一个复杂项目还可能存在以下版本：

- 产品版本；
- API 或协议版本；
- 数据库结构版本；
- 插件接口版本；
- 依赖库版本；
- 配置格式版本。

它们不应为了“看起来统一”而强制使用同一个数字。产品版本描述整套软件发布；协议和数据格式版本描述各自的兼容契约。只有当它们确实同步演进时，才应绑定。

正确做法是明确关系，例如：

```text
产品 3.2 支持 API v2
产品 3.2 使用数据结构版本 7
插件接口兼容范围为 4.x
```

这样既能统一产品身份，也不会让不同生命周期的版本互相牵制。

## 9. 推荐的版本控制流程

一套通用流程可以保持在七步以内：

1. 根据兼容性和发布通道决定目标版本。
2. 将目标版本写入唯一事实源。
3. 自动同步所有镜像版本。
4. 校验所有组件、构建配置和运行时读取结果一致。
5. 提交版本变更，并在该提交上创建同名标签。
6. 从标签构建产物，让产物展示并携带同一版本。
7. 将标签、产物和发布记录关联起来。

其中第 4 步是版本治理的关键控制点。它应回答：

- 所有必需的版本字段是否一致；
- 是否存在多余的人工维护字段；
- 当前发布通道是否接受该命名；
- 平台派生版本是否有效；
- 运行时是否能返回完整版本；
- 标签名是否与版本完全一致。

## 10. 常见反模式

- 前端、后端和安装包分别维护自己的版本。
- 正式版本写在多个文件中，依赖发布者逐个记得修改。
- 构建时从分支名、日期或最近标签猜测版本。
- 界面显示正式版本，日志却显示旧版本或固定默认值。
- 为适应平台数字字段，直接丢弃整个项目的预发布命名。
- 把产品版本、API 版本和数据库版本强行绑定。
- 标签已经发布后仍被移动到新的源码提交。
- 同一个版本号生成多个内容不同、无法区分的安装包。

## 11. 可复制到新项目的版本政策模板

新项目可以直接填写以下内容：

```text
版本事实源：____________________

版本格式：MAJOR.MINOR.PATCH[-CHANNEL.IDENTIFIER]

发布通道：
- dev：________________________
- preview：____________________
- rc：_________________________
- stable：_____________________

必须同步的镜像：
- _____________________________
- _____________________________

版本消费者：
- 应用界面：___________________
- 后端/接口：__________________
- 安装包：_____________________
- 系统文件属性：_______________
- 日志和诊断：_________________

平台版本映射：_________________

标签格式：v<完整版本号>
标签策略：推送或发布后不可移动

一致性检查入口：_______________
```

## 12. 最终检查清单

- [ ] 只有一个位置决定完整版本号。
- [ ] 其他版本字段都是同步值或派生值。
- [ ] 前端、后端、安装包和运行时显示一致。
- [ ] 版本号符合既定的语义和通道命名。
- [ ] 受限平台使用明确的数字映射，不另建版本体系。
- [ ] 产品版本与 API、数据结构等独立版本没有混淆。
- [ ] 标签名与完整版本完全一致。
- [ ] 标签指向用于构建该版本的精确源码。
- [ ] 已公开标签不会被覆盖或移动。
- [ ] 每个发布产物都能唯一追溯到版本和源码。

一套成熟的版本控制方法，最终应让团队不再问“这里的版本要不要也改”，而是能够确定：版本只在一个地方被决定，所有其他组成部分都会可靠地得到同一个答案。
